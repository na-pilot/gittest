# Sourcing Radar

4050 이커머스 바이어를 위한 로컬 Python·Streamlit 관제판입니다. 네이버 쇼핑/데이터랩, 유튜브, 인스타그램 릴스, 구글 트렌드의 반응도를 모델링하고 1688 검색어와 발주 검수 항목을 SKU별로 제안합니다. 기본 데이터는 3개 섹터의 각 20개 키워드(총 60개 SKU)에 대한 **시뮬레이션**입니다. 공급가와 환율도 계산용 가정입니다.

## Windows에서 실행

Python 3.10 이상을 준비하고 PowerShell에서 프로젝트를 엽니다. 이미 이 프로젝트의 가상 환경에 패키지가 설치되어 있다면 설치 명령은 건너뜁니다.

~~~powershell
cd D:\20codex\gittest
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
~~~

첫 번째 PowerShell에서 수집 스케줄러를 실행합니다.

~~~powershell
.\.venv\Scripts\python.exe main_orchestrator.py
~~~

같은 폴더의 두 번째 PowerShell에서 대시보드를 엽니다.

~~~powershell
.\.venv\Scripts\python.exe -m streamlit run dashboard.py
~~~

브라우저에서 [로컬 대시보드](http://127.0.0.1:8501)를 엽니다. 대시보드와 스케줄러 중 먼저 실행한 쪽이 `sourcing_radar.db`에 데모 이력을 한 번 채웁니다. 기존 데모 DB를 업데이트할 때는 기록된 SKU 점수를 보존하고 10분 구간별로 빠진 키워드만 채웁니다. 전일 순위 비교를 위해 직전 24시간에 해당하는 비교용 이력도 함께 생성합니다. 스케줄러는 시작 즉시 첫 배치를 수집하고 기본 600초 간격으로 이어서 수집합니다. 24시간 운영 시 PC가 절전 모드로 전환되지 않도록 설정하고 스케줄러를 켜 두세요. 종료는 `Ctrl+C`입니다.

간격 변경 또는 한 번만 실행하는 명령입니다.

~~~powershell
.\.venv\Scripts\python.exe main_orchestrator.py --interval 10
.\.venv\Scripts\python.exe main_orchestrator.py --once
~~~

기본 예시 환율은 1 RMB당 200원, 판매 수수료는 12%입니다. `--krw-per-rmb 205 --platform-fee-pct 10`처럼 바꾸면 이후 배치가 새 가정으로 카드의 원가와 마진을 계산합니다. 테스트 DB를 쓰려면 두 PowerShell에서 동일한 절대 경로를 `RADAR_DB_PATH` 환경 변수에 설정합니다. 스케줄러만 실행할 때는 `--db 경로`도 지원합니다.

## 화면 읽는 법

- **기간과 카테고리**. 전체를 선택하면 섹터별 TOP 20을 비교할 수 있고, 한 섹터를 선택하면 해당 랭킹을 넓게 봅니다. 상단 조회 기간은 KPI, 추천 보드와 로그에 적용됩니다. 이들의 오늘·7일·30일은 한국시간 달력 날짜 기준입니다.
- **인기 검색어 랭킹**. 조회 시점 직전 30×24시간의 배치 종합 지수를 SKU별로 합산합니다. 30일이 지난 점수는 집계에서 제외되고 DB에는 보관됩니다. 24시간 전을 기준으로 계산한 같은 길이의 누적 순위와 비교하며, 그 비교 구간에 관측이 없으면 `NEW`로 표시합니다. 주력 채널은 채널별 가중 기여도 합이 가장 높은 채널입니다. 배지 위에 마우스를 두면 네 채널의 기여도를 볼 수 있습니다.
- **종합 지수**. 네이버 35%, 유튜브 25%, 인스타그램 20%, 구글 20%를 적용합니다. 채널 누락은 빈 값으로 보관하며, 유효한 채널이 두 개 이상이면 해당 채널의 가중치 합으로 나눕니다. 오늘의 최다 바이럴 채널은 선택 카테고리에서 오늘 유효 반응도의 평균이 가장 높은 채널입니다.
- **소싱 카드**. 선택 기간의 최신 관측 지수 순으로 후보를 표시합니다. 중문·영문을 선택하고 코드 블록의 복사 버튼으로 검색어를 가져갑니다. 카드에는 같은 판매 단위 기준의 RMB·KRW 원가 범위, 국내 목표 판매가, 4050 구매 고민, 마케팅 소구점과 샘플 검수 항목이 들어 있습니다.
- **예상 마진율**. 판매가에서 환산 원가 범위의 중간값, 판매 단위당 물류·포장비, 판매 수수료를 빼고 판매가로 나눕니다. 관세, 세금, 광고, 반품 비용은 별도입니다. KPI는 조회 범위에서 관측된 고유 SKU의 현재 예시 마진율을 평균한 값입니다.
- **수집 상태**. 다음 실행까지 남은 시간은 DB에 기록한 스케줄 기준입니다. KPI는 5초, 랭킹·카드·로그는 30초 단위로 화면에서 읽습니다. 로그는 스케줄러 전체의 채널별 성공, 누락, 실패 상태를 기록합니다.

## 구성과 확장

| 파일 | 역할 |
| --- | --- |
| `sub_agents.py` | 카탈로그 적격성 필터, 4개 채널 공급자, 가중 점수, 소싱 전략과 마진 계산 |
| `database.py` | SQLite 스키마, 데모 이력 시딩, 배치 단위 저장, 30일 누적 랭킹 |
| `main_orchestrator.py` | 배치 진행 표시, 스케줄 저장, 다음 배치 재시도 |
| `dashboard.py` | Streamlit 필터, 섹터별 TOP 20 랭킹, KPI, 소싱 카드, 채널 로그 |

`MultiChannelTrendScout`에 4개 키(`naver`, `youtube`, `instagram`, `google`)로 `ChannelProvider` 구현을 주입할 수 있습니다. 각 공급자의 `fetch(candidates, observed_at)`은 SKU별 0–100점을 반환하고, 관측할 수 없는 SKU는 생략합니다. 실제 공급자는 각 API 요청에 타임아웃과 호출 제한을 설정하세요. 실제 카탈로그의 `Candidate`에는 목표 판매가, 판매 단위, 분류와 검증된 원가를 입력합니다. 공산품은 4050 타깃, 4만–10만원, 대량 소싱 적합 조건을 검사합니다. 뷰티는 지정한 기초·디바이스 유형만 통과하며, 식품은 지정된 스틱·분말 유형과 `일반식품` 분류가 모두 필요합니다.

실제 공급자를 연결할 때는 시뮬레이션과 분리된 DB 경로에 `RadarOrchestrator(..., origin="live")`를 사용하세요. 대시보드의 `open_database()`에서도 `initialize(seed=False)`를 호출하고 실제 수집으로 모드 표기를 바꿉니다. SQLite에는 점수와 채널 로그를 계속 누적합니다. 한 DB 파일에는 스케줄러 한 개를 연결할 수 있고, WAL을 사용해 대시보드는 스케줄러가 저장하는 동안에도 읽을 수 있습니다. 이전 버전의 `radar_status.json`에는 SKU별 채널 신호나 소싱 사양이 없으므로 새 SQLite 이력은 별도로 시작합니다.
